# Repository and Object Storage Contracts

Type: grilling
Status: resolved
Blocked by: 02, 04, 06

## Question

What deep repository and object-store interfaces let SQLite/PostgreSQL and filesystem/S3 adapters share behavior without collapsing to their weakest implementation?

Decide transaction boundaries, tenant-context enforcement, idempotency keys, per-account concurrency, schema/migration ownership, note and learning log/snapshot structures, asset manifests and object keys, reset/deletion jobs, backup/retention/GC rules, adapter configuration, startup validation, and conformance requirements.

## Answer

The repository and object-storage contract is:

1. `SyncRepository` exposes domain operations, not raw SQL, and accepts an authenticated `AccountContext` rather than an arbitrary caller-provided account id. Account-generation writes execute through one `withAccountWrite(accountId, expectedGeneration, operation)` transaction. SQLite acquires the write transaction up front with bounded busy retry; PostgreSQL locks the account state row and classifies deadlock/serialization failures for complete-operation retry. Object-store I/O never occurs while a database transaction holds the account lock.
2. A change is unique by `(account_id, generation, domain, change_id)` and stores its payload hash and account-generation-local receipt sequence. The same key and hash returns the original receipt without reapplying; the same key with different bytes returns `IdempotencyConflict`. Ordering uses a high-water mark on the account-generation row rather than a global sequence.
3. Use Drizzle ORM for repository queries, schema management, and migrations. Maintain one canonical, backend-neutral server schema specification as the source of truth; generate thin SQLite (`sqlite-core`) and PostgreSQL (`pg-core`) Drizzle projections and dialect-specific migration artifacts from it. The projections and generated SQL are build artifacts, not independently hand-maintained business schemas. One ordered logical migration id/checksum stream ties both dialect outputs together, and CI drift checks fail when either output is stale or semantically divergent. Backend adapters contain only driver/pool wiring, transaction and locking primitives, classified database errors, and genuinely dialect-specific capabilities. Drizzle's SQLite projection is reusable with supported React Native drivers such as Expo SQLite/OP-SQLite, while the server can use `better-sqlite3` or PostgreSQL. Startup rejects checksum changes, migration gaps, and schemas newer than the binary; migrations complete before Hono/libp2p readiness.
4. A reset is a logical generation switch, not synchronous physical deletion. Under the account lock it creates an empty generation, marks the prior generation deleting, invalidates old cursors, and commits durable deletion jobs. Current-generation APIs can never reach old data after commit. Snapshots record generation and high-water sequence; tombstones remain until active device frontiers acknowledge them or an explicit retention rule permits expiry.
5. Deletion, reclaim, garbage collection, and integrity work use durable database leases with stable job identity, owner, expiry, and attempt count. PostgreSQL may claim queue rows with `FOR UPDATE SKIP LOCKED`; SQLite claims under its write transaction. An expired lease is recoverable by another worker, and no correctness invariant depends on a process-local mutex.
6. `ObjectStore` is a small port: `putImmutable`, `get`, `head`, idempotent `delete`, and paginated maintenance-only `list`. Canonical keys are tenant- and generation-local, for example `tenants/<account>/generations/<generation>/objects/<hash-prefix>/<sha256>`. Uploads stream-verify byte length and SHA-256. Filesystem publication uses a same-directory temporary file, flush, and rename; S3-compatible publication uses conditional writes where available and verifies an existing key with `HEAD`. Multipart upload ids remain adapter-private.
7. The relational manifest is authoritative because the database and object store have no distributed transaction. Creation puts immutable bytes before committing the manifest; failure may leave a grace-period orphan, never a ready manifest without expected bytes. Reclaim leases the manifest, performs idempotent object deletion, and then records completion. Reset commits the new generation and jobs before physical deletion. Orphan sweeping waits beyond the maximum upload/workflow duration, while integrity scanning verifies the inverse manifest-to-object relationship. Backup, WAL, object-version, and disaster-recovery purge SLAs are configured and disclosed separately from live-store deletion.
8. Ship SQLite and PostgreSQL repository adapters plus filesystem and S3-compatible object adapters. SQLite and filesystem are single-host deployment semantics; network SQLite and independent multi-host filesystem storage are unsupported. Multi-instance deployment requires PostgreSQL and S3-compatible storage. Startup validates the selected topology. Shared conformance suites cover both repository adapters, both object adapters, and all four authoritative workflow combinations, including real S3/R2 compatibility jobs in addition to isolated local fixtures.
