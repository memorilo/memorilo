# Sync Protocol and Mode Semantics

Type: grilling
Status: resolved
Blocked by: 01, 04, 05

## Question

What transport-neutral protocol and state machines preserve direct P2P while adding Relay Sync Mode and Authoritative Sync Mode for Note, Personal Learning Sync, and assets?

Decide peer roles and negotiation, namespace-specific cursors/frontiers, push/pull ordering, idempotency and acknowledgement, online-only relay routing, authoritative plaintext merge/snapshot behavior, mode enable/disable and switching, membership/reset generation, clearing server data, stale client handling, bounded frames/chunks, retry/backoff, error codes, and user-visible recovery states.

## Answer

The new `/memorilo/sync/1` protocol and policy semantics are:

1. Use one transport-neutral `/memorilo/sync/1` protocol. The first message declares the peer role (`device` or `server`), credential proof, supported namespaces and modes, the client's reset generation, membership/policy epochs, and a fresh nonce. Noise authenticates the libp2p PeerId, but account authorization comes only from the application credential. The server derives the authenticated account/device context and never trusts account or generation fields as repository selectors.
2. Note, Personal Learning Sync, and assets each have an independent cursor/frontier. Changes carry a device-monotonic sequence and stable idempotency/change key. Sessions use bounded `pull -> ack -> push -> ack` phases; repository operations are account- and generation-scoped, and duplicate changes or batches return the original acknowledgement without reapplying effects.
3. Relay Sync Mode is online-only forwarding. The server maintains a bounded, account-scoped registry of authenticated live connections and forwards changes only while source and destination devices are connected. It stores no change, snapshot, or asset payload. A relay acknowledgement means accepted for best-effort delivery during the current server lifetime, never durable recovery. Devices retain a local outbox and retry after reconnect; undelivered data may be lost on disconnect or server restart, and UI states this explicitly.
4. Authoritative Sync Mode persists plaintext changes, snapshots, cursors, tombstones, and asset manifests as an additional peer. It uses the same deterministic merge/CRDT logic as the desktop adapter. A change is acknowledged only after its log/snapshot transaction commits for the current account generation. Asset bytes use a separately authenticated object stream; sync frames carry only manifests and content hashes.
5. Sync mode is an account policy with a monotonically increasing policy epoch. Administrators can disable relay and authoritative independently. A disabled mode rejects new sessions and drains existing sessions with `mode-disabled`; it never silently downgrades an account or changes the confidentiality/recovery contract. Switching relay to authoritative starts persistence at an explicit new generation after user confirmation. Switching authoritative to relay requires explicit confirmation of whether retained server data is kept or cleared; relay then makes no recovery promise. Historical data is not silently reinterpreted.
6. Clearing authoritative data is a step-up-protected, idempotent asynchronous reset/deletion job. It freezes account writes, closes active sync sessions, removes Note, Personal Learning Sync, asset manifests/objects, cursors, and tombstones in the defined scope, increments reset generation, and preserves account metadata and device memberships unless account deletion is separately requested. Old cursors, credentials, and membership epochs are rejected; clients receive `account-data-reset` and must bootstrap again. The server and UI state that cleared data cannot be recovered offline from the server; only an authorized client or another peer that still has the data can repopulate it.
7. Assets are content-addressed and immutable. A manifest is exchanged first, then bytes move over a bounded object-transfer stream authenticated by the same account/device context. Size, hash, MIME, concurrency, and timeout limits are enforced independently from control frames. Unreferenced objects are eligible for later garbage collection.
8. Use finite exponential backoff with jitter and reset it after a successful session. Retry only transport closure and timeout failures. Credential revocation, protocol mismatch, policy rejection, generation conflict, and rate limits stop automatic retry and surface an actionable state (`re-pair`, `bootstrap`, `wait-for-device`, or `administrator-action`). The initial configurable limits are 1 MiB per control/change frame, 256 changes per batch, 768 KiB decoded payload per batch, 30 seconds idle and 2 minutes total session deadlines, and bounded per-connection/per-account authenticated streams. Strict schemas reject missing, wrong-type, excess, invalid-enum, unsafe-integer, and oversized fields; frame headers are rejected before body allocation, and writers honor stream backpressure.
