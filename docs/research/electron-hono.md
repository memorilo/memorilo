# electron-hono mechanism review

Research date: 2026-08-16

Upstream repository: [`daqi/electron-hono`](https://github.com/daqi/electron-hono)

Reviewed revision: [`0b26a111de8a92c7fd1467fc086eb108f515d456`](https://github.com/daqi/electron-hono/commit/0b26a111de8a92c7fd1467fc086eb108f515d456)

## Conclusion

`electron-hono` does not start a Hono HTTP listener. It uses Hono as an in-process
request router inside Electron's main process and carries a simplified Fetch-like
request and response over one Electron IPC channel:

```text
Vue renderer
  -> window.electron.fetch(path, RequestInit)
  -> preload ipcRenderer.invoke("fetch", path, RequestInit)
  -> main ipcMain.handle("fetch")
  -> Hono app.request(path, RequestInit)
  -> simplified response DTO
  -> preload response-like object
```

Hono's official source describes `app.request()` as a testing convenience. It
constructs a Web `Request` and dispatches it directly through `app.fetch`; no TCP
socket or HTTP server participates. [Hono `request()` implementation](https://github.com/honojs/hono/blob/v4.9.4/src/hono-base.ts#L474-L503)

## Request path

The main entry imports the Hono application and immediately calls
`handleFetch(serverApp)`. This registers the IPC handler before the Electron window
is created. [main entry](https://github.com/daqi/electron-hono/blob/0b26a111de8a92c7fd1467fc086eb108f515d456/src/main.ts#L1-L7)

The handler accepts a URL string and `RequestInit`, then calls
`app.request(input, requestInit)`. It consumes the returned `Response` as text and
returns a plain object that Electron can serialize. [IPC fetch handler](https://github.com/daqi/electron-hono/blob/0b26a111de8a92c7fd1467fc086eb108f515d456/src/fetch.ts#L1-L33)

The preload exposes `window.electron.fetch`. It invokes the IPC channel and builds
an object with `json()` and `text()` functions from the returned body string.
[preload bridge](https://github.com/daqi/electron-hono/blob/0b26a111de8a92c7fd1467fc086eb108f515d456/src/preload.ts#L1-L36)

The Vue example uses relative routes such as `/users` and `/posts`, so the renderer
looks like it is using Fetch even though every call is dispatched in the main
process. [renderer example](https://github.com/daqi/electron-hono/blob/0b26a111de8a92c7fd1467fc086eb108f515d456/src/App.vue#L6-L29)

## Hono application

The Hono application defines GET and POST routes for users and posts. A Hono
middleware places a Drizzle `better-sqlite3` database in the request context, and
POST bodies are validated with `@hono/zod-validator` and schemas generated by
`drizzle-zod`.[routes](https://github.com/daqi/electron-hono/blob/0b26a111de8a92c7fd1467fc086eb108f515d456/src/server.ts#L1-L42)
[database middleware](https://github.com/daqi/electron-hono/blob/0b26a111de8a92c7fd1467fc086eb108f515d456/src/db.ts#L1-L21)

The routes query SQLite directly. There is no transport-independent application
interface between the Hono routes and persistence.

## What it does not use

The repository does not use:

- `@hono/node-server`, `serve()`, `listen()`, or another production HTTP adapter.
- `hono/client`, `hc<AppType>`, or Hono RPC type inference in the renderer.
- A real `Request` or `Response` across Electron IPC.
- Streaming, WebSocket, SSE, request cancellation, or server-push transport.
- A structured error envelope or per-route error model.
- IPC handler removal or coordinated shutdown for in-flight requests.

The development Vite server only serves and reloads renderer assets; it is not the
Hono application server. [Vite renderer exposure](https://github.com/daqi/electron-hono/blob/0b26a111de8a92c7fd1467fc086eb108f515d456/vite.base.config.ts#L65-L99)

## Fetch compatibility limits

The preload declaration says its function returns `Promise<Response>`, but the
runtime object is only a partial imitation. [global declaration](https://github.com/daqi/electron-hono/blob/0b26a111de8a92c7fd1467fc086eb108f515d456/src/global.d.ts#L1-L6)

Important differences from a real `Response` include:

- Response headers are not transported.
- The response body is always fully buffered and decoded as text in the main
  process, so binary responses and streaming are not preserved.
- `arrayBuffer()`, `blob()`, `formData()`, `clone()`, and the real `ReadableStream`
  body are absent.
- The reported `bodyUsed` value is captured before `response.text()` consumes the
  body and is not updated afterward.
- The synthetic `json()` and `text()` methods can be called repeatedly, unlike the
  one-shot body semantics of a real Fetch response.

On the request side, Electron serializes IPC arguments using the Structured Clone
Algorithm. Functions, promises, symbols, DOM objects, `File`, and several other
values cannot be sent to the main process. Therefore arbitrary Fetch `RequestInit`
objects, streams, DOM `FormData` payloads, and `AbortSignal` cannot be assumed to
survive this bridge. [Electron `ipcRenderer.invoke`](https://github.com/electron/electron/blob/v37.3.1/docs/api/ipc-renderer.md#L124-L172)

## Errors, lifecycle, and security

If `app.request()` or response serialization throws, the `ipcMain.handle` promise
rejects. Electron only transports a serialized error and does not preserve the
original main-process error object or its custom properties. [Electron
`ipcMain.handle`](https://github.com/electron/electron/blob/v37.3.1/docs/api/ipc-main.md#L90-L125)

The single `fetch` channel does not inspect the invoking sender, frame, origin, or
route authorization. Exposing a narrow preload function is better than exposing
`ipcRenderer`, but renderer code can invoke every Hono route accepted by this
bridge. A production application still needs sender checks, route authorization,
payload limits, admission control, timeouts, and shutdown ownership.

The SQLite connection is opened at module initialization using `./sqlite.db` and
has no explicit close path in the template. [database initialization](https://github.com/daqi/electron-hono/blob/0b26a111de8a92c7fd1467fc086eb108f515d456/src/db.ts#L1-L18)

## Browser portability

The renderer attempts to select `window.electron.fetch || window.fetch`. In a
normal browser where `window.electron` is undefined, accessing `.fetch` throws
before the fallback can be evaluated. Even with optional chaining, the repository
does not provide an HTTP listener for browser `fetch('/users')`. The Hono routes
are reusable, but a browser frontend would still require a real Hono runtime
adapter such as `@hono/node-server`. [renderer fallback](https://github.com/daqi/electron-hono/blob/0b26a111de8a92c7fd1467fc086eb108f515d456/src/App.vue#L6-L12)

## Relevance to Memorilo

The useful idea is not the partial `Response` implementation. It is that the same
Hono route module can be dispatched in two ways:

```text
Electron frontend -> IPC fetch adapter -> Hono app.request()
Browser frontend  -> HTTP adapter      -> Hono app.fetch
```

A production Memorilo version should differ from the template in these ways:

1. Keep transport-independent application modules behind their existing
   interfaces. Hono routes and Electron IPC handlers should be adapters at the
   same seam, rather than moving application behavior into routes.
2. Define request, success, and failure schemas per operation. Reuse Effect Schema
   in both the IPC and Hono adapters.
3. Serialize an explicit request DTO containing URL, method, headers, and body
   bytes. Serialize a response DTO containing status, status text, headers, and
   body bytes. Reconstruct a real `Response` in preload.
4. Use Hono's custom Fetch support with `hc<AppType>` if Hono RPC ergonomics are
   desired. Split route types by domain to avoid one very large inferred type.
5. Keep Electron-only operations such as native menus, window capture, shutdown
   save handshakes, and `WebContents`-owned sessions outside the portable Hono
   interface.
6. Keep configuration and Note update subscriptions on dedicated IPC events for
   desktop; map them to SSE or WebSocket only for a browser adapter.
7. Preserve Memorilo's existing operation supervision, structured remote errors,
   resource scopes, sender validation, and deterministic shutdown behavior.

This produces real leverage: the application implementation remains local, the
desktop frontend avoids opening a network port, and a later browser frontend can
reuse the same Hono routes through a real HTTP adapter.
